# 后续回合训练的最小实验设计（独立候选）

本说明来自代码和已完成的 native campaign cycle 1 的只读检查。它不改变活动
训练、冻结 V4 或现有 native batch 时序，也不是对后续实验效果的保证。

## 先判断失败发生在哪里

两组 cycle 1 共观察到 18 场完整对手比赛、6 次失败的自然投币尝试：

| 实际小局序号 | 胜 | 负 |
|---|---:|---:|
| R1 | 15 | 3 |
| R2 | 10 | 8 |
| R3 | 2 | 3 |

R2/R3 的对手组成和比分经过前面比赛筛选，不能用这张表直接证明“第二局
自动变难导致失败”。同一模型也只完成了少量路线，不能推断总体胜率。

具体而言，native campaign 002 的三场 Ryu 是 `胜负负 / 负负 / 胜负负`；
001 的 Guile、Chun-Li 都是 `负负`，Honda 是 `胜负负`。既有先赢后输，
也有 R1 本来就打不过。对应的 cycle 1 **训练期间随机采样**统计中，Ryu
分别为 5 胜 66 负、28 胜 31 负；Sagat 分别为 25 胜 52 负、2 胜 53 负。
这些混合了持续更新的策略，不能当作最终模型的确定性评估胜率，但足以说明
当前不应把全部失败归因于 R2/R3 分布差异。

## 普通难度不代表内部状态固定

所有已检查局面的 `effective_difficulty` 都是 3，但日志里的内部量会变化。
例如 campaign 002 首次第四场 Ryu：

| 回合开局 | native pips | ai_rank | ai_index | ai_parameter_a / b |
|---|---|---:|---:|---|
| R1 | 0:0 | 163 | 20 | 56 / 216 |
| R2 | 1:0 | 205 | 25 | 56 / 216 |
| R3 | 1:1 | 201 | 25 | 56 / 216 |

R1 成熟结算时 rank 为 201；变化不仅出现在换局瞬间。另一场 Ryu 在输掉
R1 后，R2 开局 rank 从 R1 开局的 156 变为 184；不能据此归纳成简单的
“玩家赢一局就加难、输一局就减难”规则。

这是原生 RAM 观测，说明状态确实不同；**这些变量的名字不是完整的反编译
结论**，没有据此证明参数对 CPU 策略的因果机制。尤其不能把 rank 当成
DIP 难度，更不能写 RAM 去调低它。

现有两个 Ryu 训练 R1 的 rank 是 167、165，parameter_b 都是 216，和
上述完整路线第四场的 R1 接近。训练不是只采了“首位对手的低 rank 开局”。
但它只从这些 R1 起步，并在首局成熟后恢复，因此从未自然训练这些轨迹的
R2/R3；两件事必须分开。

## 最小改动：小局仍是 episode，整场才重新加载

建议下一项独立实验首先解决状态覆盖，不同时改奖励、网络或动作库：

1. 从已有训练池的 R1 存档加载，照旧运行 12 个原生帧的动作和批量 PPO。
2. 小局成熟时照旧记录一次胜负和 reward，结束这个 PPO episode。
3. 如果对手比赛尚未结束，**不加载存档、不重建 Core**。让同一个 Core
   保留比分、rounds 和生命周期，在 Lua 内用中立输入自动走过结算及开局。
4. 原生 R2/R3 达到同部署端的可行动边界后，清空观察历史，复制四份新的
   局面作为下一 episode 的首观察，再让同一个模型出招。
5. 仅在整场成熟胜负后，从训练池选择下一个对手的 R1 并加载。

这不需要新增 R2/R3 采集工具，也不需要放松现有 `Core.new` 的零比分 R1
断言。后续回合已经由同一 Core 的 `between → begin_round → fighting`
流程处理，它能按实际比分接受后续开局。

胜负仍是每小局 ±1，伤害仍是当前权重；PPO 的 `done/episode_start` 在每
个小局边界重置，GAE 不越过该边界。这样隔离检验“更多原生回合状态是否
有用”，也保留 344 维观察、15 动作及已有权重兼容性。它还没有把整场获胜
显式变成长期回报目标；若覆盖改善后仍有必要，再单独比较整场 episode。

当前输入不含原生 pips 或 AI rank。对单小局获胜目标，先保留这个接口，
让模型在不同原生上下文中学习稳健应对。AI 参数可以记入诊断，暂不作为
策略输入，否则就是另一个信息接口实验。

## batch 内的边界需要明确处理

当前 `batch_runtime.lua` 在 `#core.rounds > 0` 时直接将 episode 视为结束，
随后调用 checkpoint reset；每次 reset 又用 `Core.opening(...,{0,0})` 和
`Core.new` 创建 R1 状态。不能只把终止条件改成 match complete，就假设
其余逻辑仍然正确。

新实验需要独立维护两套计数：

- **Core 比赛生命周期**：持续到 native 两胜，`core.rounds` 不清空。
- **PPO 小局生命周期**：新成熟的 round-result 相对 `recorded_round_count`
  只消费一次；return、steps、history 每小局重置。不能把旧 R1 结果重复
  当成 R2 的结果，也不能每帧因 `#core.rounds>0` 重复奖励。

最后一个动作的训练记录保留它执行前的观察，以及成熟结算时计算出的奖励、
终止状态和 native round。Lua 自动走到下一小局可行动边界，才向批次提供
新首观察。若这时已经达到批次预算，返回的 `observation` 是这个新首观察、
`episode_start=true`；不是结算 pose，也不是还没 ready 的初始化帧。

过场不应制造新的空动作决策，也不能计入 12 帧动作的 active-frame 计数。
Core 和原生时间仍每帧检查，新的动作计时只在真正 fighting 时推进。

**不要把补满血当作伤害奖励。** 首局奖励必须以首局成熟状态为终点算完；
R2 首观察作为新的奖励基准。否则从残血跳到 144 的恢复会污染伤害差分。
`done=true` 也必须和 rollout buffer 的下一 `episode_start=true` 一致，
避免把另一小局的价值作为上一局的终局 bootstrap。

匹配部署的要点是复用 native Core 的 R2/R3 行动门、历史重置和 frame_done
首输入时机，而不是在发现满血、timer99 的第一个回调就提前行动。Core 的
`round.opening` 是候选开局，可能早于实际首次决策；审计要使用事件 frame
和首决策 frame，而不能只比较保存的 opening 时间戳。

## 吞吐与采样预算

保持 8 workers、每个 rollout 256 次决策、既有 block 传输；过场和原生
续局在 Lua 内自动运行，Agent 不参与，每小局不新增 Python 往返。
恢复存档次数会减少，但自然过场增加了模拟帧，因此**不能预先承诺总吞吐
更高**。应同时记录：

- 实际训练决策/秒、原生 fighting/settling/between 帧数；
- checkpoint load 次数、自然续局次数、每个 round index 的样本数量；
- 按对手及开局 pips 分组的胜负、未完成片段、无效执行；
- 相同预算下自然投币整场胜率、失败对手及路线推进深度。

选对手仍以整场 reset 为边界；因为有些对局打两小局、有些打三小局，按
对手均匀选比赛不再保证小局数严格均匀。先完整报告这个差异；如需弱项
加权，应在新实验开始前固定采样方式，不在连续验证途中调整。

对照保持相同初始化模型、训练开局池和决策预算，只改变是否自然接续小局。
观察新分布有没有帮助，与网络变大、伤害权重调整、额外宏动作等因素分开。

## 已有日志可以直接回答什么

无需中断活动模拟器，可只读每场 JSON：

- `rounds[].outcome/score/opening/stop/settled`：小局结果、比分及三个时间点的
  完整状态，包括 `ai_rank/ai_parameter_a/ai_parameter_b/ai_index`。
- `events`：match/round start、stop 和成熟结果的实际帧，可检查后续回合
  就绪时机。`native_timing_audit` 已检查所有 fighting 决策的 12 帧覆盖。
- `trace.columns/rows`：全部原生帧的血量、位置、动作、动画、比分、时间和
  DIP/内部难度，可比较首次攻击、受击、位置及动作选择轨迹。
- `trace.decisions`：当时双方状态、实际按键序列及选择帧，可复原当前 15
  动作模型的决策；分析应使用动作前的状态，不能使用未来画面作输入。

**全帧 trace 没有 AI rank/index 列**。只有完整状态快照和结算 trace 保留
这些量，因此不能从当前证据声称已知它们的逐帧变化、RNG 种子或未记录的
CPU 私有记忆。现有 JSON 也不是完整 save-state，不能反向生成一个真正的
R2 存档。若以后需要后续开局池，必须在独立训练采集中实际保存，且按来源
轨迹分割，不能把同一场的 R1 放 train、R2 放 holdout。

## 实现前的验证门槛

新增实验模块，保持当前正在运行的源文件冻结。先用强制相同动作在新训练
运行时与 native 部署端比对**跨 R1→R2、R2→R3 和整场结束**的原生轨迹，
包括小局奖赏只发一次、history 重置、开局 pips、12 帧首输入、预算恰好
落在终局边界，以及平局后继续。测试不能只覆盖又一次 R1 load。

native parity 通过后再跑同预算吞吐对照和小额真实 PPO 更新。若检查失败，
保留无效记录并停止该实验；不影响原有 campaign 自主继续运行。


## 独立候选实现

`round_chain_runtime.lua` 复用同一个 `native_continuous_core.lua` 到整场成熟结束；
每个新小局结果只消费一次，终局 reward 使用其原始 `settled` 快照，下一小局
的 episode/history 只在部署 Core 实际调用首个动作选择时重置。若 batch
恰好在终局用尽，Lua 仍自动走到下一小局真正可行动的边界后才返回；不会
以满血补充制造上一小局的奖励，也不会把结算阶段当作新的空动作。

`round_chain_builder --output DIR` 从默认包构建隔离候选；`--source PATH`
也接受已有的 16 动作冻结包，不改变其动作库和权重接口。所有派生文件和
来源均记录 SHA256，默认执行源不变。候选结果带 `round_chain=true`，并记录
loads、natural_rounds、各阶段原生帧数、matches、逐小局 round/score/result。
完整比赛额外保存一份带原生决策帧的强制重放动作计划。旧 `--native-parity`
只检查 R1，候选入口明确拒绝它，避免两份新采样器自比冒充独立部署证明。

`test_round_chain.py` 使用原始 Core 测试 R1→R2→R3 生命周期、同比分确认
平局后继续、整场结束才加载、恰好终局预算、终局奖励与新血量隔断，以及
15/16 动作包构建。离线测试不等于模拟器验证。

`round_chain_parity` 是独立原生验证工具，需要真实捕获的 255 动作平局计划。
它先用候选采样器自然打完整场，再关闭该模拟器，以
`chain_reference_runtime.lua` 单独驱动部署 Core，用捕获动作重放整场，
逐原生帧比较状态、事件、phase、round，以及小局结果和决策边界。参考端
只在开局加载一次，全场不暂停、不读档；这仍是训练诊断，不计正式通关。
后续启用训练还需要真实 PPO 更新与吞吐验证，不应仅据此宣称学习效果改善。

早期原生 probe002 在一个有限样本中逐帧通过 10289 帧、640 个动作，完整结果为
`draw / win / loss / win`，包含 R1→R2→R3→R4 和整场结束。独立离线复审
保存的 rollout 进一步验证全部 640 个动作的 4×86 观察历史、4 次且仅
4 次终局奖励和 GAE 的 done/start 隔断；最大观察误差为浮点序列化量级
5e-15。第一份参考 probe 因诊断初始化缺少速度设置而无效，原记录保留。
这不是任意批次边界的等价性证明：后续整场重放发现暂停恢复会让下批首招
在同一原生时间提前被端口锁存，早期样本未暴露该问题。详见
[NATIVE_TIMING](NATIVE_TIMING.md#batch-resume-input-latch-correction)。

16 动作派生包另保存 `parent-build.json` 与其 SHA，使用专用 chain schema
和完整父源身份，不伪装成原 actions16 build。派生 support 会在 native
验证前后检查 chain/父包的接口、来源、文件和模型；动作与观察模块必须
保持父包原字节。真实训练吞吐和自然投币验证仍需另行检查。

16 动作小额真实 PPO 对照也已完成：同一迁移初模、seed、2 workers、各
2048 次决策，两者都实际更新了参数。chain 采样为 173.85 decisions/s、
总耗时 28.76 秒；R1 对照为 175.85 decisions/s、28.62 秒。运行时与其他
训练共享机器资源，这个短样本只说明没有观察到显著吞吐损失，不能当作
稳健的速度提升结论。chain 本次累计 9 次加载和 7 次自然续局，确实采到了
后续小局。新权重随后自然投币验证一轮：Blanka 2:0、Guile 2:0、Honda
0:2，为有效失败；native 时序及 chain/16 动作接口审计全部通过。该小试
验证了训练到独立部署的路径，没有证明通关能力或收益优于 R1 训练。

`round_chain_trial` 不要求 actions16 构建目录另有 `src/`。它优先复用父包
已经冻结的 `src/astra_play_sf2`；没有时解析当前 Python 环境中实际安装的
`astra_play_sf2`，连同 assets 冻结到试验目录。也可用
`--production-source /path/to/astra_play_sf2` 显式指定包目录。来源和逐文件
SHA 保存在 `production-source.json`，并由 trial 结果引用；chain、R1 对照
和 native 验证统一使用这份生产依赖快照。


## 后续修正的证据边界

随机探索另遇到非超时双 KO：双方原生血量均为 `-1`，timer 为 65，比分
保持 1:1；旧动画名单不能认出该终态。独立 v4 结算候选要求双方原生 KO、
显示血量单调落到 `-1`、比分及 timer 不变、旧局至少成熟 360 原生帧，
再由同角色/同比分/满血 timer 99 的真实下一轮确认平局。它保存旧局成熟
快照用于奖励，确认快照单列，不把下一轮补血算作伤害，也不复活已 invalid
的 Core。真实失败 trace 的 587 个终态帧及反例测试保留为离线证据。

在复现这条路径时才发现跨 batch 的首招锁存缺陷。修正应恢复与无暂停
部署相同的输入相位，不能为了重现旧 `win/loss/draw/win` 路线保留错误输入。
因此新的整场 parity 比较修正后实际生成的轨迹；旧双 KO 结算证据和新的
输入时序证据分别报告。600 帧初步 gate 已用实际 IN1/IN2 及全状态验证
首次 33 决策批次边界；该 gate 本身不代表整场通关或学习效果提升。


修正后的完整新轨迹随后通过 4889 原生帧、316 决策的逐帧核对，结果
`win/win`，包括 R1→R2、首次 33 决策批界和后续 64 决策批界。参考端
仅初始加载一次，场内不暂停；观察、两次成熟奖励和 GAE 隔断均通过。
另一个 600 帧三路径检查把首次显式 `reset→rollout` 也纳入覆盖：它和
`reset_rollout`、无暂停 reference 的全状态一致，前 460 帧实际 IN1/IN2
均一致。新 gate 因而同时用于初次暂停开局及普通批次恢复。这些有界证据
不等同于所有动作序列均已证明，更不计为正式通关。
