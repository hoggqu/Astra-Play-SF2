# Normal 全对手训练方案审查

这是实现前的工程判断，不是实验结果。目标是让一个学习模型在 Normal（原生
难度 3）下自然投币、无 continue、无读档、对局内不停顿，取得一次完整的
十一对手通关。冻结 V4 只用于采集和对照，不在学习模型失败时接管动作。
正式 V4 的验证认证与这个新策略身份分开。

## 建议的第一条路线

1. 用冻结 V4 在自然投币路线中收集全部十一名对手的满血 R1。每个对手预先
   划定 train/dev/holdout；不能把同一轨迹的相邻帧分到不同集合。保存产生的
   时间扰动和所有采集败局保留。不同文件哈希不是独立性的证明。
2. 保留现有 344 维观察、15 动作、12 帧决策与 64/64 MLP 作为首个共享模型
   基线，避免同时改变网络、奖励和动作空间。观察中已经有对手身份。
3. 每次 reset 先均匀选对手，再在该对手的训练开局中抽样。可以在预先规定的
   阶段边界增加弱项比例，但保留所有角色；只均匀抽存档会偏向样本较多者。
4. 保持已批准资源：两个 8-worker 服务，总 CPU 配额 20 个逻辑 CPU、内存
   上限 24 GiB、静音无窗口。可比较随机初始化与 Blanka 权重续训；两者均
   在同一 Normal 数据上训练。续训是迁移实验，不是假定最高难度可以直接通用。
5. 用足够长、自动执行的阶段训练，阶段末保存模型并按每个对手单列结果。
   所有阶段无需 Agent 修改动作规则。遇控制错误停下保留现场，不能重放含糊
   的输入请求；正常败局由程序继续处理。
6. 冻结候选模型后导出推理权重，在新的自然投币完整路线中验证。第一阶段只
   要求一次通关；这不等于证明高通关率。尝试数、所有失败对手和无效执行仍
   必须报告，不能只展示成功的一轮。

## 时间预算应主要用于采样

旧实验 102400 决策的训练时间约 712 秒，总时间约 940–953 秒；差值约占
24–25%，包含启动、评估、保存和关闭，不能全部归因于通信。

单对手一次 dev 为三小局。扩至十一对手后一次变为三十三小局，因此照搬
每 10240 决策一次全量评估，会大幅提高评估成本。建议首轮每 102400 决策
全量 dev；若需更频繁反馈，可以预先固定单个 lead 作轻量 dev，再定期全量。
不要在看到结果后临时挑选更容易的 lead。固定基线只需建立一次，避免每阶段
重复跑相同基线。初始化模型的全量失败评估可以省略，但要在协议中明确。

阶段选模至少记录每对手胜率与等权平均胜率。可使用预先固定的排序：最低
对手胜率、等权平均胜率、平均回报。三小局估计很粗，最低值常为零，不能把
它当精确总体能力；完整自然游玩仍是目标对应的验证。

## V4 行为克隆不能直接当成无损捷径

当前 `actions.lua` 的十五类动作不是 V4 输出序列的完整集合。例如 V4 使用：

- 2 帧等待/防守；模型动作每次固定 12 帧。
- MP 升龙及不同输入速度；现有 uppercut 使用 LP。
- 前方向加 HP 的近身投；现有 fierce 只有 HP。
- 火球之后持续防守的长序列；现有 fireball 尾段为空输入。
- 受击或换边后取消队列；当前训练模型仍执行到 12 帧边界。

V4 还读取具体动画标识 `anim`，并由每原生帧历史计算 `attack_age`、`vy`、
`rebound`；344 维观察没有动画标识，四次稀疏观察不保证能还原这些条件。
因此，同一个学习输入可能对应不同教师动作，且语义相近的标签执行后也可能
产生不同结果。不能把 V4 完整胜率当成这十五动作的教师上限。

若需要模仿预训练，先选择并标记一种方式：

- **有损语义投影：** 通过 V4 所选序列映射 fireball/uppercut/sweep/guard 等
  宏动作。先让这个投影教师单独运行 dev，测量其可执行胜率和未覆盖比例，再
  决定是否生成大量标签。训练标签来自动作执行前的相同历史输入，不能把未来
  12 帧的状态放入输入。投影规则和教师版本独立记录。
- **新的保真动作接口：** 将实际序列整理成有限、带持续时间的动作词表，增加
  缺失可观察特征，重新定义模型接口和训练。连续推理也必须同步更新；旧 15
  动作模型不可直接使用。该路线工程面更大，不宜悄悄混入首轮基线。

行为克隆数据只来自 train 开局，不得用 dev/holdout 轨迹训练。高动作分类
准确率也不等于高实战胜率：偏差累积后模型会进入教师数据没覆盖的状态。
如果 BC 后继续 PPO，报告为“模仿初始化 + PPO”，而不是随机初始化 RL。

## 连续推理一致性是先决条件

导出 MLP 后需用固定观察比较 Python 与 Lua 的 logits/argmax；处理精度边界
和相同分数时的选取规则。动作顺序、Tanh、层权重方向、归一化/裁剪、历史
顺序、12 帧计数以及每次决策时固定的左右方向都必须匹配。

尤其不能直接用 `Core:drive` 的队列取消机制代替训练动作执行：它在受击和
换边时会清空队列，而训练非 baseline 路径没有这种取消。Core 可继续用于
逐帧胜负成熟检查，但其 V4 动作输出不应进入学习模型游玩。

每小局历史应独立初始化，不把前局结算帧混入观察。R1 存档重置的实际开始
时刻与 Core 在 R2/R3 的原生就绪门可能不同，必须在真实连续游玩中检查。
每局使用相同模型文件，期间不暂停、不替换参数，不允许失败时 V4 接管。

## 首轮可能暴露的真正短板

- R1-only 训练缺少 R2/R3 的 RNG、开局姿态和时间分布。可在新训练采集中
  增加实际后续回合开局，但加载校验和训练终止逻辑都要支持对应原生比分；
  不能只改掉 `Core.opening(...,{0,0})` 断言而忽略胜局计数。
- 每次十二帧决策限制反应时机；扩大网络不能解除动作持续时间限制。
- 四次状态历史只覆盖短时间，缺失动画细节可能让某些反击条件不可区分。
- dev 上的 3/3 不意味着总体胜率 100%；十一场比赛组合会放大弱项影响。
- 用 holdout 的输赢决定追加训练后，该集合已参与开发决策，后续应作为 dev
  而不是继续声称独立测试。新的自然投币完整路线可以提供下一阶段外部检查。

遇到这些问题时按证据选择一次接口变更，并重新记录策略身份；不要同时调整
奖励、网络、宏动作和采样方式，以免无法知道改善来自哪里。
