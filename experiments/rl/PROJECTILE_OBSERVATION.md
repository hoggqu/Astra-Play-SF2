# 飞行道具观察候选：资料与有限实机验证

**当前 PPO 没有新增飞行道具特征。** 本文只记录后续候选：先完成当前训练预算；
若 Ryu 对局仍长期停滞，再考虑验证和加入该观察。方向仍是一套共享神经网络
对付全部对手，保留现有动作接口，不加入按对手切换模型或脚本代打。

## 来源与版本

这两份来源是实现代码和直接逆向记录，均不是 Capcom 官方规格：

- [FBNeo 训练模式的 SF2 hitbox 脚本](https://github.com/peon2/fbneo-training-mode/blob/master/hitboxes/sf2-hitboxes.lua)：
  `sf2` 配置给出对象池起点 `0xFF938A`、8 个槽、步长 `0xC0`，
  使用状态字 `0x0101`，X/Y 为槽地址 `+0x06/+0x0A` 的有符号字。
- [SF2 引擎逆向记录](https://github.com/ROMArchaeology/sf2-lineage/blob/main/engine/ENGINE.md)：
  记录 Pool C 的 type 0 波动拳、对象 `+0x2A` 血量，以及所称的
  玩家/对象指针字段 `+0x1D4/+0x26`。
  [ROM 版本清单](https://github.com/ROMArchaeology/sf2-lineage/blob/main/verify/romsets.json)
  可用于核对版本。该项目含 AI 辅助逆向，字段解释需要独立实测。

本项目使用 MAME 0.288、`sf2` / World 910522。按该版程序 ROM 的偶/奇字节
布局重建 CPU 程序映像后，CRC32 为 `43fcc23e`，SHA-1 为
`6bb03cf7a2b39d39fb3e9656f8bcd3a5915524f0`，与上述逆向资料的 World rev G
来源对应。映像身份匹配只确认版本，不证明字段解释正确；本文不分发 ROM 字节。

## 实机方法与观察范围

独立训练诊断从一个 **train 池 Ryu 开局**加载一次，使用冻结的 16 动作共享
神经策略，连续观察 3600 原生帧。只在私有运行副本的快照函数中增加对象池、
候选指针及原始血量读取；不写游戏 RAM，不改模型输入、动作或奖励，不读取
holdout。原生帧间隔为 0.016768 秒，对局中没有暂停。到预算即结束，整场未
结束，结果为 partial，不能算作正式通关或胜率认证。

共出现 18 个 `status == 0x0101` 区间，其中按低地址字关联归于 Ryu 的有 11 个、
Ken 的有 7 个，最后一个被预算截断。**888 个对象帧样本**同时满足状态字
`0x0101`、对象 HP256；它们不是 888 次独立发射。所有这些样本的 owner 读数
高 16 位都对应玩家地址低字，该玩家 projectile 读数高 16 位又对应对象槽地址
低字，关联一致率为 888/888。

观察到 Ryu 波从 x702 移动到 x612，随后波 HP 由 256 变成 -2，同时 Ken
原始 HP 从 144 变成 125；下一帧玩家关联字段清零，再下一帧槽状态清零。
显示血量则逐帧追赶原始血量。另观察到双方波 HP 同帧变为 -1、双方玩家血量
不变，随后两槽消失，与互消语义吻合。这些是生命周期和伤害对应证据，
不是经过反事实试验的完整碰撞判定证明。

## 不能直接照搬的字段解释

1. **状态字不是完整的活波判据。** 波 HP 变负后，`0x0101` 还会保留 1–2 帧；
   出屏时还见到 `0x0100, HP256`。必须区分存活、已命中/互消、退出中的对象，
   不能把所有存在的槽当成仍可造成伤害的波。
2. **上述 u32 读取不是已验证的完整指针。**
   `read_u32(player+0x1D4)` 例如得到 `0x98CA0007`，
   `read_u32(object+0x26)` 例如得到 `0x86C60000`。
   高 16 位提供低地址字关联证据，但字段宽度、对齐及相邻数据仍未知。
   不能直接 `& 0xFFFFFF` 当地址，也不能据此断言偏移应整体减 2。
3. 本次只覆盖 Ryu/Ken、type 0、Y96 的波及两个对象槽。
   Guile 音速手刀、Sagat 高/低虎波、其他槽和完整 owner 生命周期均未验证。
   输入序列符合定义也不等于实际端口锁存已验证；这是另一项独立检查。

## 后续最多一个观察候选

确认读取协议后，每方增加 **活波标志、相对 X、相对 Y**，共 6 个标量；
明确相对坐标基准、无波编码和死亡对象过滤条件，并验证双方与所有相关对手。
若进入实验，冻结新的观察身份，用同预算对照及全部对手的自然投币验证衡量
收益，避免仅改善 Ryu 而损害其他对手。共享网络与动作集合保持不变。

现有距离特征并未出现明显常量或全被裁剪的问题：对 4182 个 train 示范观察，
有 510 个不同距离值，范围约 -0.594 至 0.602，裁剪比例 0%，且与双方 X
坐标差的归一化一致。因此，这只是有实证依据的新增信息候选，不能把缺少
飞行道具位置直接称为当前网络的性能硬上限。

本文仅保留方法、有限统计和限制；原始逐帧轨迹、训练存档与模型不随文档分发。


## Guile / Sagat 的四个有界 train 探针

新增可复用入口 `python -m experiments.rl.projectile_probe --source PACKAGE_DIR
--model MODEL.zip --dataset MANIFEST.json --output NEW_DIRECTORY`。默认只取
Normal 清单中 Guile/Sagat 各两个 train 开局，顺序启动四个独立实例，每个
最多 3600 原生帧；dev/holdout 文件不会打开。源包和生产依赖先复制，再仅
向诊断快照附加对象字段。冻结模型仍接收原有 344 维观察、输出原有 16
动作；没有训练、奖励调整或游戏 RAM 写入。

这次四个探针耗时约 86 秒，均运行满 3600 帧后截断为 **partial**。
总计 14400 原生帧；各实例只在开始加载一次，场内不暂停。它们不计入胜率。

| train 样本 | CPU `0x0101` 区间数 | CPU 正 HP 对象帧 | CPU type / Y |
|---|---:|---:|---|
| Guile 1 | 3 | 54 | type 3 / Y90 |
| Guile 2 | 10 | 252 | type 3 / Y90 |
| Sagat 1 | 14 | 328 | type 4 / Y118、Y78 |
| Sagat 2 | 0 | 0 | 预算内未观察到 |

Sagat 第一个样本的 11 个区间位于 Y118，3 个位于 Y78；正 HP 对象帧分别
为 217 和 111。这确认同一 type 4 有两种高度，和高/低虎波的预期相符，
**type 本身不能区分两者**。低位对象的命中/格挡生命周期未在这批数据中
得到确证。Guile 的 13 个区间均为 type 3 / Y90。Ken 对象仍为 type 0 / Y96。
这次只出现槽 6、7，不能外推为八个槽都已验证。

全部 2403 个正 HP、status `0x0101` 对象帧的 HP 都是 256，owner 地址低字
和所属玩家的槽地址低字互相一致（2403/2403）；这是对象帧关联率，不能当作
2403 次独立发射。新增相邻 u16 读取与原 u32 的高低字完全一致，进一步
说明应保留字段宽度疑问：玩家 `+0x1D4` 的高字可关联对象，低字却可为
1 或 7 等非零值，不能把整个 u32 当作已证实的对象指针。

生命周期证据也扩展到了 CPU 波：一个 Guile 对象在 frame 237 从 HP256
变成 -2，同时 Ken 原始 HP 从 144 变为 112；一个 Sagat Y118 对象在
frame 104 出现同类变化，Ken HP 从 144 变为 111。另有 Guile HP 变成 -1
且玩家 HP 不变的事件，与消除语义相符；也有同帧玩家受伤，因此不能只靠
某个负值或同帧伤害断言唯一的碰撞原因。对象 HP 为负后状态仍可暂留
`0x0101`，出屏也可保留 `0x0100/HP256`。这些数据支持区分正 HP 活动对象
与消失阶段，尚未证明完整的可伤害判据。

未追加探针来填补第二个 Sagat 样本或低波命中证据。当前模型输入未改变；
任何后续特征实验仍须有新观察身份和独立、完整的自然投币验证。


## Dhalsim 补充探针

同一只读工具增加 `--opponents 7`，使用两个独立 train 开局，各最多
3600 原生帧。这两次共耗时约 43 秒：第一个达到 3600 帧后保留 partial，
第二个在 3139 帧自然整场结束，因此按预算规则提前停止。两者均只加载
一次、场内不暂停；整场结束也不把这类训练诊断计为正式胜负样本。

第一个样本出现 6 个 CPU type 1 / Y80 区间，共 365 个正 HP 对象帧；
还出现 3 个 type 2 区间。第二个没有 type 1，但有 4 个 type 2 区间。
type 2 共 204 个正 HP 对象帧，Y 在 69/70/82/99 间变化，不能与前述
平移波不加区分地解释。

含 Ken 对象在内，共 575 个正 HP 对象帧都能根据对象 owner 低字关联到
玩家，但只有 570 个同时满足玩家到槽的反向关联。五个不匹配样本全部
是 type 2 消失前最后一帧：玩家 link 已经清零，而槽仍为 status0101、
HP256。另有 type 2 HP 变成 0 后再消失。这说明不能把 status0101/HP256
直接当作所有攻击对象的完整活动判据，也不能把负 HP 的解释照搬到 type2。

没有为填补覆盖而追加探针。新增六标量的候选定义、按四个历史块迁移
权重及 optimizer 的方案见[接口设计](PROJECTILE_INTERFACE_DESIGN.md)；
目前只有设计文档，没有改变模型接口或启动新观察的 PPO。
