# 难度设置修复（0.1.1）

0.1.0 在 MAME 启动后才修改 DIP，并把端口读回正确当作难度生效的证据。
SF2 World 910522 已缓存难度，这个检查不足以证明游戏实际采用了请求档位。
用户在 Windows 上发现五档分别启动后的过程相同；随后在 macOS 上复现了
请求最高难度、DIP 正确但内部仍为 Normal 的问题。

| 本机短启动对照 | 请求档位 | DIP 对应档位 | 游戏内部档位 | 首战内部 rank / index |
|---|---:|---:|---:|---:|
| 旧启动流程 | 3 | 3 | 3 | 56 / 7 |
| 旧启动流程 | 7 | 7 | 3 | 56 / 7 |
| 启动前写入原生配置 | 7 | 7 | 7 | 112 / 14 |

以上是开局诊断，不是通关或胜率实验。ROM 主程序 CRC32 为 `43fcc23e`；
使用本地 ROM 的反汇编核对了下面的数据流。地址仅适用于这个 ROM 版本。

## 游戏如何读取难度

1. ROM `0x171A` 读取总线 `0x80001C` 的 DIP B，取反后写入 RAM `0xFF808B`。
2. ROM `0x18B0..0x18B8` 将该镜像与 `7` 按位与，写入 16 位值 `0xFF82C6`。
   它是游戏解码后的难度，数值与 CLI 的 0–7 档位一致。
3. ROM `0x4148` 读取这个缓存，用于从 `0x99A48` 表中选择参数，随后计算
   `0xFF8A04` 的 rank 和 `0xFF89CE` 的索引。它们是动态游戏状态，不要求
   在整轮中保持固定，也不通过修改这些值来设置难度。

仅看菜单、DIP 端口或输入镜像都不充分。可靠的运行条件是：端口低三位等于
`7-level`，镜像低三位和内部难度均等于 `level`。

## 新启动与验证方式

Python 在启动 MAME **之前**创建运行目录内的 `cfg/sf2.cfg`，同时保存不可变的
`boot-config.xml` 和哈希。MAME 正常开机读取该设置；Lua 启动阶段只读验证，
不再运行时改档。

单档多次挑战使用同一进程，自然结束后投币；不会在每次失败后重启。
`--difficulty all` 使用顺序运行的五个独立会话，各档开机前配置好难度，
结果汇总到同一个根报告。切档的新会话发生在挑战之外；没有局中重置、
读档或写 RAM，也没有更改 V4 的 fighter、Core 或 selection。

启动、投币前及每场开局检查实际难度；每个 Core tick 被动记录并检查端口、
输入镜像和内部值。异常会拒绝开赛或作废当前对局，保留证据。新的单会话
格式为 `astra.run.v2`，跨档汇总为 `astra.batch.v1`；根审计同时核验子会话
身份、策略及 Core 一致性、预算、启动配置、内部读数与逐帧记录。

## 旧成绩的处理

原始成绩和文件保留。旧 `astra.run.v1` 缺少内部难度证据，新审计会显示
`Difficulty unverified`，不会自动填入请求档位并认证。报告仍可展示原始
记录和临时统计，但不得作为新版本已确认难度的通关率。

更早的训练与 Coin22 历史也只核验过 DIP，跨难度结论需要重新验证。不能
直接假定它们全部运行在 Normal：旧环境的启动配置与此次 CLI 不同。
V4 字节身份没有改变；是否能在修复后的各档稳定通关，要由新实验回答。

先做五档开局值核验、错误缓存拒绝检查和同档自然投币测试，再做完整路线。
单元测试与本机 MAME 实测分别记录，Windows 实机结果也应单独报告。
