# 原生开局等待（0.1.2）

旧流程每次挑战前无条件空跑 9000 帧，正常速度约 151 秒，目的是让
上一轮的 Continue 倒计时或通关结局自然结束。首次开局也使用同一个
等待，且游戏提前回到待机后仍等满预算。

新版由 `entry.lua` 逐帧读取游戏任务状态，在连续两帧满足条件时返回。
Python 等到就绪结果才发送一次投币，随后等待原生标题转场完成再发送
一次 Start。9000 帧仅为每个等待的超时上限；超时会保存诊断并判无效，
不重发输入、不重置、不跳过结局，也不修改游戏 RAM 或冻结的 V4 策略。

## 识别条件

以下地址通过本地 `sf2` World 910522、主程序 CRC32 `43fcc23e` 的
反汇编与实机对照核验；不适用于未经核验的其他版本。

任务表位于 `0xFF0000`，每项 32 字节，首字节为零表示该任务不存在。

| 任务地址 | 用途 |
|---|---|
| `0xFF0000` | 开机流程 |
| `0xFF0020` | 待机及演示 |
| `0xFF0040` | 投币后的标题/Start 流程 |
| `0xFF0060` | 玩家输入，包括 Continue |
| `0xFF0080` | 游戏流程，包括对局和通关结局 |

投币条件：仅待机任务存在，其他四项不存在，并且原生输入回放标志
`0xFF82DA` 为 1。Continue 和结局期间仍有游戏任务，不会满足该条件。
ROM `0x6604` 创建投币标题任务并退出待机任务；`0x6E8A` 附近创建游戏
任务；`0x9A28` 和 `0xB0B8` 附近在游戏结束后重建待机任务。

Start 条件：仅投币标题任务存在，回放标志为 1，`0xFF8000` 的 16 位
模式值为 4，且 `0xFFDD59` 的画面特效忙标志为 0。模式 4 提前出现：
ROM `0x6D0A` 仍会等淡入淡出结束，之后 `0x6D0E` 才检测 Start 边沿。
只检查模式值会漏掉这个等待，导致过早的 Start 被忽略。

不能用角色血量判断待机，因为演示对战也有角色与血量。
`0xFF831B` 的结局标志可能在回到待机后尚未清零，故仅记录它，不用它
阻止新投币。只等任务退出，也不会截断结局或误把新游戏当作续关。

## 记录与验证

每次挑战的 `readiness.coin` 和 `readiness.start` 保存等待帧数、预算、
稳定帧数、结果和 RAM 读数，包含在运行清单及证据封存中。包含新
`entry.lua` 的运行必须通过这两项审计；旧 0.1.1 证据继续按其原有
规则审核，不会伪造它没有采集的就绪记录。

改变等待时长会改变自然投币的时刻及随机数序列，因此对手顺序、逐局
结果可能变化。策略文件保持冻结，但既往逐局成绩不代表这次一定重现。

本机诊断：正常速度首次等待为 **580 帧、约 9.9 秒**，另有既有的
5 秒 autoboot 启动阶段。投币后的 Start 就绪等待为 33 帧。
在进行中的玩家对局内，用 2 帧预算测试得到 timeout；单独的诊断随后
保持无输入，让该场自然败北并走完 Continue，共 5574 帧才回到待机，
随后再次投币、等待 80 帧即可 Start，并核验了新的 Ken 首回合。
这些是流程诊断，不计入冻结打法的通关率。
